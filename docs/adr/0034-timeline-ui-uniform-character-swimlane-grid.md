# Timeline UI — uniform character-swimlane grid (non-proportional, order-based)

**Status**: accepted. Supersedes the **UI surface** of ADR-0033 (whose agent-tool surface — the `timeline_lookup` tool — remains accurate and unchanged).

The Timeline UI renders as a **uniform character-swimlane grid**: one horizontal row per Character (the "lane"), entries (Events and Scenes) drawn as **equal-width cards positioned on a shared chronological-order axis** — not a time-proportionate one. Columns are the pure chronological-order index at uniform width; a header axis labels each column with its entry's real `startAt`. A multi-character Event produces one compact card per participant lane, and because every lane shares the same axis, those cards auto-align vertically at the same column — the "convergence" reading (who was present together) emerges from geometry alone, with no connectors or spokes. Zero-participant entries collect in a bottom "Unassigned" lane; undated entries (`startAt === null`) occupy a marked "Undated" zone at the right end of the axis (ordered by id, i.e. creation order). Lane visibility is a client-side multi-select (default: Characters with `participationCount > 2`); the `TimelineQuery.characterId` filter is NOT wired to lane selection — lanes are a display layer over the full result set, not a query restriction. Every Event and Scene is its own card — there is **no absorption** of Events into referencing Scenes; cross-references are shown via the `narratedBySceneNames` / `narratedEventNames` annotation fields. This matches the agent tool's chronological-truth projection and retires ADR-0033's "intentional divergence" between the two surfaces — both now show every entity at its own `startAt`.

This replaces three failed rendering attempts, all of which assumed a time-proportionate primary axis: (1) hand-rolled SVG swimlanes with a packed node belt and radial spokes (ADR-0033's design — too much bespoke geometry to render correctly), (2) `react-calendar-timeline`, a Gantt library whose duration-proportionate bars made short events sub-pixel-invisible on millennial spans, and (3) gap-positioned cards, which lost the time axis the user explicitly asked for. The sub-pixel failure is structural, not implementational: on a 1920px viewport a one-year event on a 250,000-year span is ~0.008px wide — to render it at 1px the ribbon would need to be ~250,000px (≈130 screens of scroll). Research across Aeon Timeline, World Anvil, Plottr, and Campfire shows that every surviving worldbuilding tool ships a **non-proportional, order-based view** (Aeon "Subway View" — "even spacing… not linear, does not represent relative time spacing"; World Anvil "List Mode" — "one after another, regardless of duration or gaps"; Plottr's entire model) as the readable default, often alongside an optional proportional band; and that academic fisheye/logarithmic alternatives are unproven and actively hurt target acquisition and spatial judgment (Cockburn et al.; Hornbæk). The uniform swimlane grid is that proven paradigm; the equal-width card guarantees a one-day event and a millennial span stay equally readable.

Click-on-card opens a popover with the full entry context (name, time, location, participants, description excerpt, cross-references) plus an explicit "open detail" action — navigating to the Event detail route for events, or the Novel chapter workspace for scenes. This satisfies R2 ("view information or jump to detail") without accidental navigation from the dense grid.

**Additive schema extension (exemption to the "frozen" data contract).** Scene-to-novel navigation requires `TimelineEntry` to carry `novelId` and `chapterId`; it currently carries only `novelTitle`. This is an **additive** change — two new nullable fields on scene entries (`None` for events), no break to existing consumers — and is the single deliberate exemption to the otherwise-frozen Timeline data contract. The Rust `query_timeline` command already joins scene→chapter→novel to resolve `novelTitle`, so emitting the two ids is trivial; the agent tool benefits symmetrically (it can now cite the exact chapter). No other field on `TimelineEntry`, `TimelineQuery`, `TimelineResponse`, or `TimelineLane` is altered.

**Scope.** The MVP ships the uniform swimlane only, which already satisfies functional requirements R1–R7. A proportional ("time-as-distance") secondary band via `vis-timeline` is reserved for a later phase; the mode-toggle UI reserves its entry point but does not implement it. Filtering maps directly to `TimelineQuery`: location / novel / item dropdowns, a `from`–`to` time range (native `datetime-local` pickers, matching the app's ISO-input convention), and an `includeScenes` toggle. Character-lane selection is the client-side display layer described above; when `total` exceeds the 100-entry cap, a banner surfaces the truncation and prompts the user to narrow filters.

Considered and rejected: **single horizontal ribbon** (loses the character-thread convergence reading the swimlane is chosen for); **time-bucketed grid** (reintroduces mild proportionality and sparse-bucket problems); **one-card-spanning-many-lanes with connectors** (the spoke geometry that sank ADR-0033); **absorption of Events into Scenes** (reintroduces the UI/tool divergence and a transform layer for no gain in a uniform-card layout); **fisheye / logarithmic axis** (academic, unused by any production worldbuilding tool, damages spatial judgment); **pure proportional band as primary** (the sub-pixel death that killed attempts #1 and #2).

Consequences: ADR-0033's UI-surface paragraph is hereby superseded — its agent-tool paragraph stands. The `Timeline` glossary entry in `CONTEXT.md` is updated to drop the "visual absorption" language and describe the uniform swimlane. The data layer gains two additive nullable fields (`novelId`, `chapterId` on scene entries). The uniform swimlane is a CSS-Grid + virtualization layout with no hand-rolled coordinate geometry (the failure mode of attempt #1), keeping the rendering layer simple enough to maintain.
