# Per-role model generation settings stored in AgentConfig as a JSON blob

The app had no way to influence generation parameters — temperature, thinking/reasoning, sampling knobs — for any role; every `streamText`/`generateText` call ran at provider defaults (plus two hardcoded one-shot temperatures). Model generation settings now live in the per-role `AgentConfig` row (`agent_configs.model_settings`, SPACE_MIGRATION_015) and are editable in the Space config dialog.

Shape of the decision:

1. **One nullable JSON TEXT column, per-field NULL = provider default.** `model_settings TEXT` holds a camelCase `ModelSettings` object (`temperature`, `topP`, `topK`, `maxOutputTokens`, `reasoning`, `providerOptions`). Mirroring the `max_steps` doctrine (ADR-0051): no NOT NULL/DEFAULT, app-layer validation in `do_update_agent_config_model_settings` (`DbError::InvalidInput`), corrupt/NULL column reads as the all-null default. The blob is replaced whole on update (the `context_compaction` struct-arg precedent); the wire object itself is ALWAYS present on a serialized `AgentConfig`, so consumers only null-check fields. Deliberately excluded: `seed`, `stopSequences`, penalties — reachable later or via the escape hatch without a migration (adding a nullable JSON key is backward-compatible on both sides).
2. **Reasoning uses the AI SDK 7 portable top-level parameter.** `reasoning` stores exactly the six effort levels (`none`…`xhigh`) and maps to the SDK's portable `reasoning`, which the SDK translates per provider (OpenAI `reasoningEffort`, Anthropic `thinking`, Google `thinkingConfig`). `'provider-default'` is not storable — that is what `null` means. `'max'` exists only in OpenAI's providerOptions layer, not the portable param, and is excluded. Unsupported combinations fail at the provider, not in our code — same posture as model binding itself.
3. **`providerOptions` is the raw escape hatch, held as `serde_json::Value`.** Power users can paste any provider-namespaced JSON (`{"openai":{"reasoningSummary":"auto"}}`). HARD constraint: the Rust field must be `serde_json::Value` (BTreeMap, deterministic sorted key order), never `HashMap` — random iteration order would churn the conversation-runtime `configSignature` and rebuild live agents on every resolve (ADR-0023). The frontend additionally canonicalizes (recursively key-sorted stringify) the signature entry so pre-roundtrip key order can never matter. Provider options take precedence over the portable `reasoning` per SDK rules — that is the documented way to force an exact Anthropic `budgetTokens`.
4. **One injection site for all loop roles, plus the two one-shots.** `constructAgent` threads `modelSettings` into `AgentLoopOptions` (the pure library already forwarded the sampling fields; this change added `reasoning`/`topK`), so orchestrator + 8 subagents are covered by the single site. `namer`/`vision` are their own seeded config rows — their settings forward through `generateConversationTitle`/`describeImage`, with the former hardcoded temperatures (0.3/0.2) demoted to fallbacks. Temperature precedence: config value → `ROLE_REGISTRY` role default (kept; still set by no role) → provider default.
5. **UI commits per field into the whole blob.** The config dialog gains a "Model parameters" section (all roles, including one-shots): a reasoning `Select` with a "default" sentinel committing NULL (maxSteps precedent), number inputs committing NULL when emptied (local-draft blur/Enter commit, contextNote precedent), and a providerOptions textarea that parses on blur and refuses to commit invalid JSON. Settings are generation knobs, not identity — changing them rebuilds the agent for the next turn via the signature, exactly like a model rebind.

The cost: one more fanned-through field on `ResolvedAgentModelConfig` → `ResolvedModel` → `AgentLoopOptions`, and a JSON blob the DB cannot constrain per key. The alternatives — typed columns per parameter (a migration per future knob, six-column fan-out through every SELECT) or a settings overlay table (join complexity for eleven rows) — buy nothing the blob does not already give, and the app-layer validation plus Zod schema keep the blob's shape honest at both boundaries.
